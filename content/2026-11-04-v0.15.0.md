## Logic aliases

There are two kinds of functions in Creusot: program functions and logic functions.
Morally, they belong to entirely different worlds (Rust vs. Pearlite),
but because Creusot piggybacks on rustc's parsing and typechecking infrastructure,
these functions appear in the same namespace. Sometimes, there are
program and logic functions that represent a common concept, and we must
add suffixes to distinguish between them.
For example:

- `len` vs. `len_logic`
- `contains` vs. `contains_logic`
- `deref` vs. `deref_logic`
- `new` vs. `new_logic`
- `leading_zeros` vs. `leading_zeros_logic`

You get the idea. We are forced to use more verbose names either in logic or in programs.

*Logic aliases* enable using a program function in place of a logic function.
For example, this declares `len` as a logic alias for `len_logic`:

```rust
impl<T> Seq<T> {
    #[logic_alias(self.len_logic())]
    fn len(&self) -> Int { ... }
}
```

That allows using `len` in specifications.

```rust
impl<T> Seq<T> {
    #[ensures(result == (self.len() == 0))] // `.len()` will be expanded to `.len_logic()`
    fn is_empty(&self) -> bool { ... }
}
```

To prevent meaningless and confusing aliases, the result of the program
function must equal its logic counterpart. This extra postcondition is automatically
inserted by `#[logic_alias]`:

```rust
#[logic_alias(self.len_logic())]
// implies
#[ensures(result == self.len_logic())]
```

The attribute `#[logic_alias]` can contain an arbitrary expression,
as long as it has the same type and the constraint above is satisfied.

This allows patching some minor differences in argument types.
For example, for Creusot's type `FSet`, the program function `contains` expects
a borrow (like other collection types in Rust),
but in logic, there is no ownership and `&T` becomes identical to `T`,
hence the logic function `contains_logic` takes an element `T`.

This logic alias enables using `self.contains(t)` in place of `self.contains_logic(*t)`,
automatically introducing a logical dereference of the argument (which translates to
the identity function because this is in logic).

```rust
impl FSet<T> {
    #[logic_alias(self.contains_logic(*t))]
    fn contains(&self, t: &T) -> bool { ... }

    fn contains_logic(self, t: T) -> bool { ... }
}
```

In practice, this means that we must artificially add an ampersand to
the argument when using `contains` in specifications instead of `contains_logic`,
which is not ideal, but it is what it is.

## Derive `DeepModel`

The trait `DeepModel` maps a Rust type to a mathematical model of it.

```rust
trait DeepModel {
    type DeepModelTy;

    #[logic]
    fn deep_model(self) -> Self::DeepModelTy;
}
```

A `DeepModel` is notably used by the specification of `Eq`: the comparison `x == y` in Rust
tells us whether `x.deep_model()` and `y.deep_model()` are equal
(for a primitive notion of equality in logic).
For example, a `Vec` is modelled by a `Seq`, the type of mathematical sequences.
Thus, comparing vectors with `==` only compares the sequence of elements they represent,
ignoring low-level details like where the elements are stored and the capacity.

Users can implement `DeepModel` for their own types, and in common situations, it can be
derived just like `PartialEq` and `Eq`. One subtlety however is that `DeepModel` contains
an associated type `DeepModelTy`. When deriving `DeepModel`, we also generate a type definition
which is a copy of the original type where all of the fields are replaced with their
deep model.

```rust
#[derive(DeepModel)]
struct S(A, B);

// expands to

struct SDeepModel(A::DeepModelTy, B::DeepModelTy);

impl DeepModel for S {
    type DeepModel = SDeepModel;

    #[logic]
    fn deep_model(self) -> Self::DeepModelTy {
        SDeepModel(self.0.deep_model(), self.1.deep_model())
    }
}
```

Another problem we had was with the visibility of the `deep_model` function.
As a logic function, there are two kinds of visibility that apply to it:
the visibility of the function name, which is the one you're already familiar
with in Rust (using `pub` or not), and the visibility of the *function body*.
When you do proofs,
it can be useful to unfold the definitions of the functions you use, on the one hand.
On the other hand, some definitions are tied to implementation details that
should remain hidden from users. To control who can see the function body,
the `#[logic]` attribute supports a sub-attribute `open`, which works similarly to `pub`:

```rust
#[logic(open)]
#[logic(open(self))]
```

Omitting `open` defaults to `#[logic(open(self))]`, which makes the definition
visible to the current module.

What visibility should we use for `deep_model`? For a `struct` with private fields like
the example above, we are constrained by the fact that the fields are private:
its accessors appear in the definition of `deep_model`, so the body must also remain private.
But for a type with public fields, it is reasonable to make the body of `deep_model` public as well.
